# CareerPilot pivot blueprint

Baseline is `integration-review` at `006cc8ce24f0709a11c7249623e6f985ffdb7a72`, with Alembic revision `adf094dd1fee`. Paths in this specification are relative to the repository root. This is the implementation and validation contract for the pivot. The checked-out application and its runtime data are outside this planning change.

CareerPilot will have two primary surfaces in the existing FastAPI/Jinja dashboard. **Vagas** discovers Remote or Recife jobs and offers **Dispensar** and **Preparar & Aplicar**. **Candidatura** prepares a truthful PDF and fills one application step in a visible, signed-in Chrome window. The user reviews and advances each portal step in Chrome, including final submission. **Preencher etapa atual** in the dashboard resumes the work after navigation, answering a question, or clearing a blocker. **Perfil mestre** edits the local source of candidate facts.

## 2. Phase 1 — Master Profile, state and tailored résumé

### Migrate data

1. Add a new Alembic revision descending from `adf094dd1fee`. Update `backend/app/models/tables.py`, `backend/app/main.py` and the scripts together. Production startup uses `alembic upgrade head` and checks the database revision. Remove `Base.metadata.create_all` from production lifespan. Tests may explicitly construct isolated schemas or run migrations. Existing databases created through `create_all` without an Alembic version require a backup and schema comparison to the initial revision before stamping. Fail with an actionable error if they differ.
2. Create `master_profiles(user_id PK, document JSON NOT NULL, revision INTEGER NOT NULL, updated_at)`. The document contains `contact` (name, email, phone, city/state/country and links), `experience[]`, `education[]`, `projects[]`, `skills[]`, `languages[]`, `preferences` (target roles, location, work model, salary amount/currency/period or free text, availability, work authorization), `standard_answers[]`, and `imports[]`. Each array item with candidate claims has a stable ID. Imports hold document hash, filename and extracted text. Include optional fields as null or absent and use empty collections for missing lists.
3. Backfill every real `ProfileFact`, including `user_verified=false`, preserving original fact IDs, values and useful metadata. Map recognized singleton contacts into typed fields and retain conflicting entries as imported notes with their source. Latest `(created_at,id)` wins a singleton tie. Translate experience, education and projects to structured entries with existing text as details, preserve skills/languages and merge explicitly configured preferences. Current defaults such as immediate availability and Brazilian work authorization lack user provenance. Leave them blank when no user-entered fact establishes them. Exclude `is_fictional_demo=true`. Keep existing real résumé IDs and artifacts.
4. Map old applications to `ready`, `review`, `needs_user` or `done`. Both `verified` and `submitted_unverified` become `done`. Keep prior `rejected`, `expired`, and `canceled` entries as historical `closed` and omit them from the active panel. Map `ready_for_manual_review` to `review`, `blocked` and `needs_user_input` to `needs_user`, and the rest to `ready`. Retain all real application IDs, even when historical rows share a job. Copy resolved `QuestionRequest` answers into the respective application's `answers_json` keyed by the old field key, without promoting them to reusable answers. Discard approval/receipt machinery after backfill. Preserve real job history and drop fictional jobs only when identified by explicit fictional source or demo provenance, never by employer-name substring.
5. Add `applications.answers_json`, `applications.last_step_json` (nullable), and nullable `resume_versions.profile_revision` and `resume_versions.job_description_hash`. Application status `ready` means PDF prepared, `review` means a fill pass completed for visual review, `needs_user` means there are actionable blockers, and `done` records user-declared completion. Persist no browser handle, credential, or receipt. Historical `review` and `needs_user` rows with no live binding display **Reabrir no navegador**. Remove `question_requests` after copying answers.
6. For SQLite batch rebuilds involving referenced parent tables, explicitly handle foreign keys outside the migration transaction on the migration connection, then run `PRAGMA foreign_key_check` and restore enforcement. Drop children before parents. Create a SQLite backup via the backup API with the service stopped and retain the artifact directory. A destructive downgrade must fail explicitly and direct the operator to that backup. Prove fresh and populated upgrades.

### Implement profile and LLM contracts

- GET `/profile` returns `{document,revision,updated_at}`. PUT `/profile` accepts `{document,revision}` with Pydantic validation and uses a compare-and-swap update. A missing row is revision 0. A stale revision returns 409 and reloads the editor. The editor supports all sections including reusable answers. Imports from `POST /profile/import` reuse the PDF/DOCX/TXT/Markdown extraction in `ResumeService`. Retain extracted text losslessly within explicit upload/text limits, parse recognizable fields into typed entries, deduplicate by SHA-256, and merge without overwriting manually entered singleton fields. Imported text and parsed fields are usable immediately. Provide edit/delete on the resulting entries and a clear error for unreadable documents.
- Extend `backend/app/core/llm.py` with async `complete_structured(..., output_model)` over the existing chat-completions transport. Support `LLM_PROVIDER=ollama` with `LLM_BASE_URL=http://127.0.0.1:11434/v1` and `LLM_MODEL=qwen2.5:7b-instruct`, and `openai_compat` with the configured URL, model, and optional bearer key. An IDE or Antigravity participates through its configured compatible endpoint or a user-provided local bridge implementing that contract. There is no Antigravity-specific transport in this checkout. Request a JSON schema where supported, otherwise request a JSON object in the prompt and validate identically in Pydantic. Reject unknown keys, malformed results, over-limit arrays and stale IDs. Allow one corrected completion for invalid structure. Use configurable timeouts and no redirect following. Treat exact parsed loopback hosts as local, replacing the current URL substring test. Keep optional paid-provider limits out of local model calls. [Ollama OpenAI compatibility](https://docs.ollama.com/api/openai-compatibility) · [Ollama structured outputs](https://docs.ollama.com/capabilities/structured-outputs)
- Pass the candidate profile and vacancy text together as separate structured inputs. Candidate facts are eligible without a verification flag. Treat job and DOM strings as content and keep the model tool-free. The prompt and output never grant browser authority, construct destinations, or select files. Default to a local endpoint. When the user configures a remote provider, show the provider destination and make transmission of candidate data an explicit provider setting (`LLM_ALLOW_REMOTE_PROFILE=false` by default). Refuse candidate-bearing model operations for a remote endpoint until it is enabled. Exclude credentials, cookies, tokens and government identifiers from model payloads. Use local deterministic resolution for stored contact values and sensitive answers where applicable. Reuse redaction and URL guards without inheriting the fictional-portal exception.
- Define `ResumePlan {language, ordered_skill_ids, experience_selections, project_ids, education_ids, summary_evidence_ids, summary_template}`. An experience selection contains a profile entry ID and the ordered IDs of its existing bullets. A summary template is an enum of localized templates with slots populated from validated facts. Structured fields and résumé bullets render from the referenced profile text. For imported document prose, allow a selection of exact source excerpts by import ID and verified offsets. Reject invented employers, skills, metrics, qualifications or altered dates by design. Tailoring changes section ordering, selected evidence, and localized summary wording. Keep the full normalized vacancy description as input and surface a retryable error if it exceeds the configured context budget. Output PDF plus extracted plain text and store selected evidence IDs for preview.
- Reuse ReportLab and pypdf from `ResumeService._render_single_column_pdf`. Add portfolio support, keep accent-capable fonts, and verify the expected contact and selected text are extractable. Render to a temporary file then atomically rename to `artifacts/resumes/<resume_version_id>.pdf`. Resolve real path under that root and verify ownership in download and upload. Commit the résumé row and application pointer together. Delete newly created files on handled failure, retain referenced older artifacts, and clean unreferenced temporary files on restart. Preserve existing authenticated GET `/resumes/{id}/preview` and `/download` with current ownership checks tightened where needed.
- POST `/applications/prepare` accepts `{job_id}`. Under a per-user/job lock reuse the newest resumable application or create one. Reuse a valid PDF for the same profile revision and description hash. Rebuild on explicit prepare after either changes. Hold no write transaction across model or rendering work and recheck versions before publishing. A completed job returns its current `done` record. GET `/applications` returns records with `id,job_id,status,resume_id,last_step,updated_at`. Missing candidate content returns 422 with an editor link. Provider failure returns an actionable retry error and leaves the previous artifact available. Deterministic offline tailoring may select source entries by keyword overlap and must display that mode.
- Phase 1 ships a working profile, prepare/preview and basic manual job-link handoff using already persisted real jobs and the existing real discovery entry point. Remove scoring from both discovery and GET `/jobs` in this phase. Keep temporary legacy discovery columns until Phase 2 removes their callers.

## 4. Phase 3 — Fill the current application step

### Open and bind the application

1. **Preparar & Aplicar** calls POST `/applications/prepare`, then POST `/applications/{id}/open`, then the first POST `/applications/{id}/fill-current-page`. Open uses the stored `job_url` in a dedicated tab, or focuses the tab already bound to that application. Never re-navigate an already bound tab on repeat open. The user opens the application flow via the portal's application entry button if the job detail has no form. Show **Abra o formulário da vaga no navegador e clique em Preencher etapa atual**. This also covers LinkedIn Easy Apply opening a modal, sign-in, and external application entry. There is no portal-specific auto-advance routine.
2. A supported portal adapter identifies the application form or modal and the vacancy identity on the observed page. Add adapters for LinkedIn Easy Apply, Gupy, and InfoJobs in `browser_automation/adapters.py`. Implement a generic candidate-form path for approved external ATS origins with an unambiguous application container. Generic code handles supported native controls. Add narrow adapters for custom widgets demonstrated by live tests. Gupy candidate-account settings and global résumé/profile edits are separate surfaces. Present an alert when a portal has no per-job résumé attachment.
3. Use POST `/applications/{id}/attach-page` for explicitly choosing an existing application tab after a handoff or restart. The dashboard lists page titles and safe origins for candidate tabs in the dedicated browser, identified by temporary server-generated IDs. It does not accept a raw URL, CDP target, or selector from the client. Display the page origin and matching job context before selection. Validate the tab still has the selected public origin and recognizable form or vacancy context. Drop the binding if the page closes, changes to an unapproved origin, or displays a different vacancy. Preserve any existing portal draft. Tell the user how to rebind or reopen on a lost page.
4. Before filling, require an owned binding, a readable PDF associated with the application. When a profile changes during a draft, continue using current user answers on explicit fill. Retain the résumé shown in the current draft and label its older profile revision. **Preparar & Aplicar** explicitly regenerates when needed. An application reopened from old history with a missing or unreadable artifact goes through prepare before filling.

### Inspect, resolve, apply and report

- `inspect_step(page)` finds one visible application container and returns a server-side snapshot with a random `step_id`, navigation generation, exact origin and URL context, form/dialog heading, stable structural fingerprint, descriptors, and blocker flags. Discover label and accessible name via explicit labels, ARIA and fieldset legend, plus type, autocomplete, required status, editable/enabled state, options, and file accept rules. Describe pre-existing values as presence/selection flags. Do not collect hidden input values, password/OTP controls, raw page HTML, script text, or unrelated account UI. Include same-origin frames only when the adapter identifies the form and can re-resolve its owner frame. Surface cross-origin form frames for manual completion. If multiple containers or controls are ambiguous, report the ambiguity.
- Resolve known candidate keys and exact saved answers first using normalized labels, semantic control types and context. Then call the gateway for unresolved controls with `FieldPlan {items:[{field_id,kind,profile_key?,option_id?,draft?,evidence_ids?}]}` where `kind` is `profile_value|choose_option|draft|manual`. The request includes the current vacancy, tailored text and profile data as needed. With no model response, keep exact mappings and surface required fields that still lack an answer. This supports motivation and project questions grounded in candidate facts. Validate IDs against the current snapshot and constrain `profile_key` to compatible field kinds. Literal contact and factual values come from the profile, never generated guesses. Drafts reference existing fact IDs and are labeled **Resposta sugerida** in the review result. For objective facts such as salary, availability and work authorization, require a saved answer or an exact supported conversion. Unknown required questions become blockers. Unsupported optional controls remain empty and appear as skipped only if actionable.
- Each descriptor has a server-side locator factory tied to the container, frame and field signature. Build locators from semantic labels or adapter-defined selectors, with safely encoded arguments. Reject ambiguous matches. Recheck binding, document, structural fingerprint and field state after model work and immediately before each mutation. If a step changed, abort remaining writes and return 409 `step_changed` with the number already written. Resolve each control fresh after dependent controls rerender. Reinspect once for newly revealed fields while still on the same step. Stop when the portal transitions away from that step. Never fill the next step in the same request.
- Apply native text/textarea via `fill`, dropdowns via `select_option`, and explicitly resolved choices via `check`/validated widget option selection. Confirm readback or the adapter's visible selection indicator. Skip nonblank fields and existing attachments by default, preserving portal defaults and user edits. Never check agreements, privacy consent, marketing, declarations, or identity attestations on the user's behalf. Keep sensitive account or ID questions in the manual path. A recognized application résumé input must have résumé semantics and accept PDF or advertise a generic file selector for a résumé. Validate the generated PDF path and artifact association, then use locator `set_input_files` or an adapter-specific chooser bound to the résumé button. Verify browser filename and portal upload completion when shown. Treat auto-upload as part of the user's explicit prepare/fill action and show the filename. Never use the same PDF for a cover letter, video or unrelated attachment. [Playwright input actions](https://playwright.dev/python/docs/input)
- GET `/applications/{id}` returns `{id,job_id,status,resume_id,last_step,updated_at}`. POST `/applications/{id}/fill-current-page` accepts an empty body, snapshots the current page, and returns `{status,step_id,filled:[{field_id,label,kind}],skipped:[{field_id,label,reason}],blockers:[{code,field_id?,label?,message,can_answer}]}`. Concurrent mutations can return 409 `operation_in_progress`. A retry on the same step reevaluates unresolved fields without reapplying already populated values. Start no write transaction before browser/model I/O. Persist the final status afterward and keep partial browser writes visible even if the report save fails. Transient CDP errors return a retryable result with reconnect guidance.
- Emit `needs_user` and **AÇÃO HUMANA NECESSÁRIA** for `login_required`, `captcha`, `video_required`, `external_assessment`, `missing_answer`, `consent_required`, `unsupported_widget`, `unknown_origin`, or `upload_failed` as appropriate. Name the affected question or action. Challenge, login and assessment views stop before field mutations. For a missing answer on an otherwise valid page, fill the other recognized controls before reporting. A provider failure leaves deterministic fills in place and identifies unresolved fields. A closed vacancy or disconnected/closed tab gets its own recovery message. No background polling triggers a fill or page advance.
- POST `/applications/{id}/answer-questions` accepts `{step_id,answers:[{field_id,value,save_to_profile}],profile_revision?}`. Accept only current, answerable blockers and revalidate the binding/snapshot. Store an application-scoped answer indexed by a stable question signature derived from normalized label, type and option labels, excluding portal-generated IDs. Upsert opted-in entries into `standard_answers` under the same signature with profile revision checking in the same transaction. For a semantically matched option from a different portal, resolve its actual option ID against the current labels. Expose editable reusable answers in the profile. Secrets and account/identity prompts remain in Chrome. After saving, offer **Preencher etapa atual** for the user to rerun the pass.
- When the step is populated, show **Revise no navegador e avance para a próxima etapa**. Only the user activates Continue, Next and Submit in Chrome. The next **Preencher etapa atual** inspects the new modal/page, including SPA transitions that keep the URL unchanged. When finished, the user may use POST `/applications/{id}/complete` via **Marcar como concluída**. Make that action idempotent with no receipt input or remote status read. The only durable completion assertion is the user's local action.
